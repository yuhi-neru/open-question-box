# 設計と実装方針

## 最優先の体験

名前も登録も必要なく、2,000文字までのひとことを送る。受信者は自分のペースで回答し、公開を個別に選択する。投稿者へ追跡可能な受取番号や会員登録を要求しない。公開回答は全員が読める。AIは外部API利用者の選択肢であり、アプリに必須ではない。

MVPは単一受信者インスタンス。公式公開サービスもこのコードで運営する。複数受信者のサービスを最初から作ると会員登録・アカウント復旧・テナント境界・悪用対策が増えるため、まず開発者本人の質問箱を完成させる。セルフホストで他の人も同じ機能を使える。

## データ

`profile`: インスタンスの名前、紹介文、受付状態。`messages`: UUID、本文、種類、状態、回答、公開フラグ、UTC ISO日時。状態はunanswered/answered/archived。公開はansweredかつ回答ありの場合だけ許可する。アーカイブ時は非公開。UUIDと日時を移行時にも保つ。

`sessions`: セッションハッシュ、失効日時。`api_tokens`: UUID、名前、ハッシュ、read/writeスコープ、発行日時。`rate_limits`: 短期間のHMACキー、回数、失効日時。`webhook_events`: 署名対象のJSON本文、再試行回数、次回送信、配信日時、送信ロック。メッセージ変更とイベント記録はD1バッチで原子的に保存する。

APIはバージョン付きのJSON。同じAPIをUIと外部連携から利用する。匿名投稿にBearerキーは不要。公開一覧は公開済み回答だけを返す。受信箱は認証が必要。特権操作は管理セッションのみ。SQLはバインドパラメーターを使用。送信bodyはストリームを上限まで読んで拒否する。

## セキュリティ

ブラウザの認証は安全なCookie、変更操作はOrigin確認。API認証はBearerでread/writeを分離。公開ページへの内容挿入はエスケープし、CSPでインラインスクリプトを禁止。埋め込みだけframe-ancestorsを許可。パス・本文のバリデーション、ログインと投稿の原子的送信制限、Turnstile再検証を実施。秘密鍵・資金は扱わない。

## 段階的拡張

1. このMVPを運用し、必要な使い勝手と迷惑投稿対策を改善する。
2. 複数受信者の公式ホスティングが必要になったら、box_idの追加、所有者認証、テナント境界テスト、削除・アカウント復旧を実装する。API互換性と単一インスタンスの移行を保つ。
3. Webhookの手動再送や冪等な投稿API、AI連携例を利用状況に応じて追加する。
4. JPYCは法的確認とテストネット検証後、任意の直接送金として追加する。投げ銭とAPI利用料は別に設計する。

API課金、AI内蔵、巨大なSNS機能をMVPに持ち込まない。アカウントの無料枠を超える場合は停止を受け入れ、有料プランへ自動変更しない。
